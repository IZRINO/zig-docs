特性亮点

小巧而简单的语言

把精力放在调试应用上，而不是调试你对编程语言的理解。

Zig 的全部语法由一个 580 行的 PEG 语法文件规定。

Zig 没有隐式控制流，没有隐式内存分配，没有预处理器，也没有宏。如果一段 Zig 代码看起来不像是跳转去调用某个函数，那它就确实没有调用。这意味着你可以确定，下面的代码只会先调用 foo()，再调用 bar()；即使不知道其中任何东西的类型，这一点也有保证：

var a = b + c.d;
foo();
bar();

隐式控制流的例子：

  • D 有 @property 函数。这类方法的调用写法看起来像访问字段，所以在上面的例子中，c.d 可能会调用函数。
  • C++、D 和 Rust 支持运算符重载，所以 + 运算符可能会调用函数。
  • C++、D 和 Go 有 throw/catch 异常，所以 foo() 可能抛出异常，导致 bar() 不被调用。

Zig 让所有控制流都只通过语言关键字和函数调用来管理，以此促进代码的可维护性和可读性。

说到性能，Zig 比 C 更快。

  • 所有 Zig 代码都位于同一个编译单元中，一起进行优化。
  • 精心选择的非法行为。例如，在 Zig 中，有符号整数和无符号整数溢出都属于非法行为，而在 C 中只有有符号整数溢出是这样。这使 Zig 能进行 C 中无法进行的优化。
  • Zig 直接提供了 SIMD 向量类型，让编写可移植的向量化代码变得容易。
  • 标准库提供了哈希表和数组列表等基本数据结构；而在 C 中，人们往往为了省事而用链表。
  • 除非交叉编译，否则默认启用 CPU 的高级特性。

手动内存管理

用 Zig 编写的库可以用在任何地方：

  • 桌面应用
  • 低延迟服务器
  • 数据库
  • 操作系统内核
  • 嵌入式设备
  • 实时软件，例如现场演出、飞机、心脏起搏器
  • 通过 WebAssembly 在网页浏览器或其他插件中运行
  • 通过 C ABI 供其他编程语言调用

为此，Zig 程序员必须自己管理内存，并且必须处理内存分配失败。

Zig 标准库也是如此。任何需要分配内存的函数都接受一个分配器参数。因此，Zig 标准库甚至可以用于独立环境（freestanding）目标。

除了全新的错误处理方式，Zig 还提供 defer 和 errdefer，让所有资源管理（不只是内存）都简单且易于验证。

Zig 也是 C 编译器

下面是用 Zig 构建 C 代码的示例：

hello.c 
#include <stdio.h>

int main(int argc, char **argv) {
    printf("Hello world\n");
    return 0;
}

$ zig build-exe hello.c -lc
$ ./hello
Hello world

可以用 --verbose-cc 查看这次执行了哪条 C 编译器命令：

$ zig build-exe hello.c -lc --verbose-cc
zig cc -MD -MV -MF .zig-cache/tmp/42zL6fBH8fSo-hello.o.d -nostdinc -fno-spell-checking -isystem /home/andy/dev/zig/build/lib/zig/include -isystem /home/andy/dev/zig/build/lib/zig/libc/include/x86_64-linux-gnu -isystem /home/andy/dev/zig/build/lib/zig/libc/include/generic-glibc -isystem /home/andy/dev/zig/build/lib/zig/libc/include/x86_64-linux-any -isystem /home/andy/dev/zig/build/lib/zig/libc/include/any-linux-any -march=native -g -fstack-protector-strong --param ssp-buffer-size=4 -fno-omit-frame-pointer -o .zig-cache/tmp/42zL6fBH8fSo-hello.o -c hello.c -fPIC

注意，如果再运行一次这条命令，不会有任何输出，而且会立即完成：

$ time zig build-exe hello.c -lc --verbose-cc

real	0m0.027s
user	0m0.018s
sys	0m0.009s

这要归功于构建产物缓存。Zig 会自动解析 .d 文件，借助可靠的缓存系统避免重复工作。

Zig 不仅能编译 C 代码，而且有一个非常好的理由让人把 Zig 当作 C 编译器使用：Zig 自带 libc。

glibc 不支持静态构建，但 musl 支持：

$ zig build-exe hello.c -lc -target x86_64-linux-musl

Hello world

在这个示例中，Zig 从源码构建了 musl libc，然后与之链接。得益于缓存系统，为 x86_64-linux 构建的 musl libc 会一直保留，之后再需要这个 libc 时可以立即使用。

这意味着这项功能在任何平台上都可用。Windows 和 macOS 用户可以为上面列出的任意目标构建 Zig 和 C 代码，并链接 libc。同样，代码也可以交叉编译到其他架构：

$ zig build-exe hello.c -lc -target aarch64-linux-gnu
$ file hello
hello: ELF 64-bit LSB executable, ARM aarch64, version 1 (SYSV), dynamically linked, interpreter /lib/ld-linux-aarch64.so.1, for GNU/Linux 2.0.0, with debug_info, not stripped

Zig 是比 C 编译器更好的 C 编译器！

这项功能不只是把一套交叉编译工具链和 Zig 打包在一起。例如，Zig 附带的 libc 头文件未压缩时总共 130 MiB。而仅 x86_64 上的 musl libc 加 linux 头文件就有 8 MiB，glibc 的头文件有 3.1 MiB（glibc 不含 linux 头文件），而 Zig 目前附带了 97 个 libc。如果简单地打包在一起，总大小会达到 776 MiB。不过，借助这个 process_headers 工具和一些老派的手工劳动，Zig 的二进制压缩包总共仍然只有大约 50 MiB；而它支持所有这些目标的 libc，还包含 compiler-rt、libunwind、libcxx 和 libtsan，同时还是一个与 clang 兼容的 C 编译器。作为对比，llvm.org 提供的 clang 8.0.0 本身的 Windows 二进制构建就有 132 MiB。

对软件包维护者友好

虽然 Zig 是自托管的，但得益于基于 WebAssembly 的自举过程，从源码构建只依赖系统的 C/C++ 工具链和 LLVM，使用标准的 CMake 构建步骤即可。

对于希望避免二进制文件的发行版，有一套文档完备的步骤，可以在不使用任何二进制文件的情况下重现 Zig。

我们希望将来能激励第三方用 C 实现一个 Zig 解释器，把这一过程缩减为 O(1) 步。

构建系统明确把系统集成当作一种意图。例如，--system <path> 标志会禁用包获取，并启用所有 -fsys=[name] 选项。这些“系统集成选项”可以在构建脚本中使用，让软件包维护者和上游开发者能够相互配合：软件包维护者需要的补丁更少，上游作者也可以针对系统集成的构建配置作出有意识的选择。

非 Debug 的构建模式是可重现的（确定性的）。
