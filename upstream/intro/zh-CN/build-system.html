什么时候该用 Zig 构建系统？

基本命令 zig build-exe、zig build-lib、zig build-obj 和 zig test 通常就够用了。不过，有时项目需要再加一层抽象，来管理从源码构建的复杂性。

例如，可能出现下面这些情况：

  • 命令行变得太长、难以处理，你希望有个地方把它记下来。
  • 你想构建很多东西，或者构建过程包含很多步骤。
  • 你想利用并发和缓存来缩短构建时间。
  • 你想为项目提供配置选项。
  • 构建过程因目标系统和其他选项而异。
  • 你的项目依赖其他项目。
  • 你想避免对 cmake、make、shell、msvc、python 等不必要的依赖，让更多贡献者能够参与项目。
  • 你想提供一个供第三方使用的包。
  • 你想提供一种标准化的方式，让 IDE 等工具能从语义上理解如何构建项目。

只要符合其中任何一种情况，项目就能从 Zig 构建系统中受益。

安装构建产物

和大多数构建系统一样，Zig 构建系统把项目建模为由步骤组成的有向无环图（DAG），这些步骤独立、并发地运行。

默认情况下，图中的主步骤是 Install 步骤，它的作用是把构建产物复制到最终存放的位置。Install 步骤一开始没有任何依赖，因此运行 zig build 时什么也不会发生。项目的构建脚本必须向待安装的内容中添加东西，上面的 installArtifact 函数调用做的就是这件事。

输出

├── build.zig
├── hello.zig
├── .zig-cache
└── zig-out
    └── bin
        └── hello

这次输出中生成了两个目录：.zig-cache 和 zig-out。第一个目录包含能让后续构建更快的文件，但这些文件不应提交到版本控制中，而且这个目录随时可以整个删除，不会有任何影响。

第二个目录 zig-out 是“安装前缀”。它对应标准文件系统层次结构中的概念。这个目录不是由项目选择的，而是由 zig build 的使用者通过 --prefix 标志（简写为 -p）指定的。

作为项目维护者，你决定把什么放进这个目录，但由用户决定把它安装到系统中的什么位置。构建脚本不能硬编码输出路径，因为这会破坏缓存、并发和可组合性，还会让最终用户感到烦恼。

基础知识

用户提供的选项

使用 b.option 让构建脚本可以由最终用户以及把本项目当作包依赖的其他项目进行配置。

请注意这几行：

Project-Specific Options:
  -Dwindows=[bool]             Target Microsoft Windows

帮助菜单的这一部分是根据运行 build.zig 的逻辑自动生成的。用户可以通过这种方式发现构建脚本的配置选项。

标准配置选项

前面我们用了一个布尔标志来指示是否为 Windows 构建。不过，还可以做得更好。

大多数项目都希望能修改目标和优化设置。为了推广这些选项的标准命名约定，Zig 提供了辅助函数 standardTargetOptions 和 standardOptimizeOption。

标准目标选项让运行 zig build 的人可以选择为哪个目标构建。默认允许任何目标；不作选择时，以宿主系统为目标。此外还有用于限制所支持目标集合的选项。

标准优化选项让运行 zig build 的人可以在 Debug、ReleaseSafe、ReleaseFast 和 ReleaseSmall 之间选择。默认情况下，构建脚本不会把任何一种发布选项视为首选，用户必须自己作出选择，才能创建发布构建。

现在，我们的 --help 菜单包含了更多条目：

Project-Specific Options:
  -Dtarget=[string]            The CPU architecture, OS, and ABI to build for
  -Dcpu=[string]               Target CPU features to add or subtract
  -Doptimize=[enum]            Prioritize performance, safety, or binary size (-O flag)
                                 Supported Values:
                                   Debug
                                   ReleaseSafe
                                   ReleaseFast
                                   ReleaseSmall

完全可以直接通过 b.option 创建这些选项，但这个 API 为这些常用设置提供了一套通用的命名约定。

在终端输出中可以看到，我们传入了 -Dtarget=x86_64-windows -Doptimize=ReleaseSmall。与第一个示例相比，现在安装前缀中的文件不同了：

zig-out/
└── bin
    └── hello.exe

测试

单个文件可以直接用 zig test foo.zig 测试；更复杂的用例则可以通过构建脚本编排测试来解决。

使用构建脚本时，单元测试在构建图中分为两个不同的步骤：Compile 步骤和 Run 步骤。如果不调用 addRunArtifact 在这两个步骤之间建立依赖边，单元测试就不会执行。

Compile 步骤可以像任何可执行文件、库或目标文件一样配置，例如链接系统库、设置目标选项，或者添加额外的编译单元。

Run 步骤可以像任何 Run 步骤一样配置，例如在宿主机无法执行该二进制文件时跳过执行。

使用构建系统运行单元测试时，构建运行器和测试运行器通过 stdin 和 stdout 通信，从而并发运行多个单元测试套件，并以有意义的方式报告测试失败，而不会让各自的输出混在一起。这也是在单元测试中写入标准输出会出问题的原因之一：它会干扰这条通信通道。另一方面，这一机制将使一项即将推出的功能成为可能，也就是让单元测试能够预期发生 panic。

在这种情况下，为单元测试启用 skip_foreign_checks 可能是个不错的调整：

链接系统库

要满足库依赖，有两种选择：

  1. 通过 Zig 构建系统提供这些库（参见“包管理”和静态库）。
  2. 使用宿主系统提供的文件。

对上游项目维护者来说，通过 Zig 构建系统获取这些库阻力最小，也把配置的权力交到了维护者手中。所有用这种方式构建的人都会得到可重现、彼此一致的结果，而且它在每个操作系统上都能工作，甚至支持交叉编译。此外，项目还可以精确地决定要基于整个依赖树中每个依赖的哪个确切版本来构建。这预计会是依赖外部库时普遍首选的方式。

不过，如果要把软件打包进 Debian、Homebrew 或 Nix 等软件仓库，就必须链接系统库。因此，构建脚本必须检测构建模式并据此进行配置。

zig build 的使用者可以用 --search-prefix 提供额外的目录，在查找静态库和动态库时，这些目录也会被视为“系统目录”。

处理一个或多个生成的文件

WriteFiles 步骤可以生成一个或多个共享同一父目录的文件。生成的目录位于本地 .zig-cache 中，每个生成的文件都可以单独作为 std.Build.LazyPath 使用。父目录本身也可以作为 LazyPath 使用。

这个 API 既支持把任意字符串写入生成的目录，也支持把文件复制进去。

输出

就地修改源文件

项目把生成的文件提交到版本控制中并不常见，但有时确实会这样做。如果生成的文件很少更新，而更新过程又有繁重的系统依赖（只在更新过程中才有），这样做就很有用。UpdateSourceFiles 提供了完成这项任务的方法。

使用这项功能时要小心：它不应在正常构建过程中使用，而应作为一个工具，由有意更新源文件的开发者运行，更新后的文件随后提交到版本控制中。如果在正常构建过程中这样做，就会导致缓存和并发方面的 bug。

$ zig build update-protocol --summary all
Build Summary: 4/4 steps succeeded
update-protocol success
└─ WriteFile success
   └─ run proto_gen (protocol.zig) success 401us MaxRSS:1M
      └─ zig build-exe proto_gen Debug native success 1s MaxRSS:183M

运行这条命令后，src/protocol.zig 会被就地更新。
