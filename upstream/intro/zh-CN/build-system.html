何时需要使用 Zig 构建系统？

基础的命令行调用（例如 zig build-exe、zig build-lib、zig build-obj 和 zig test）对于快速验证概念或小型脚本已经足够实用。然而，随着工程规模的增长，这些基础命令可能会变得力不从心。

例如，当你的项目面临以下任一情况时：

  • 命令行参数变得过于冗长繁琐，你希望有一个统一的配置文件来固定这些构建参数。
  • 你需要同时构建多个产物，或者整个构建流程包含多个相互依赖的复杂步骤。
  • 你希望充分利用多核心并发执行与细粒度智能缓存，从而显著缩减日常构建耗时。
  • 你需要为项目对外暴露灵活的编译期配置选项。
  • 针对不同的目标操作系统、硬件架构或优化级别，项目的编译逻辑需要差异化处理。
  • 项目依赖了其他外部代码库或第三方依赖包。
  • 你希望彻底摆脱对 cmake、make、shell 脚本或 msvc 等繁杂外部构建工具链的非必要依赖。
  • 你希望将自身项目打包发布，供其他第三方开发者方便地作为依赖引入。
  • 你希望为集成开发环境（IDE）等外部工具提供一套标准化的语义理解接口，便于精准提取包含路径、宏定义及编译器标志。

如果满足上述任何一种场景，引入 Zig 构建系统都将为项目带来巨大的工程收益。

安装构建产物

与绝大多数现代构建系统一样，Zig 构建系统也是基于有向无环图（Directed Acyclic Graph, DAG）来对各个构建步骤及其依赖关系进行建模的。

默认情况下，构建图中的主入口是 Install 步骤。它的职责是将编译好的二进制产物复制到最终的输出目录中。

作为项目的维护者，你可以完全自由地决定将哪些产物安装到该目录中；终端用户也可以通过 -p / --prefix 参数自定义该安装路径。

单元测试集成

单个源码文件可以直接使用 zig test foo.zig 进行测试，但对于大型项目，推荐使用构建脚本统一编排测试流程。

在构建脚本中，单元测试被清晰地拆分为两个不同的构建步骤：编译测试可执行文件与运行测试。

编译测试步骤可以像普通的可执行文件或库一样进行全面配置（例如添加宏定义、链接库等）。

运行测试步骤也可以像普通的 Run 步骤一样进行配置，例如传入测试过滤器参数。

当使用构建系统运行单元测试时，构建执行器（Build Runner）与测试运行器（Test Runner）会通过标准输入（stdin）和标准输出（stdout）进行进程间通信，以便能够并发执行多套测试套件，并以整洁规范的方式汇报测试失败信息，避免不同测试的终端输出相互混杂交织。这就是为什么在单元测试中直接向标准输出打印内容可能会带来问题——它会干扰这一通信通道。另一方面，该通信机制也让一项强大的新特性成为可能：在单元测试中预期并验证 panic 崩溃行为。

在这种情况下，为单元测试开启 skip_foreign_checks 选项是一个不错的调整：

查找并链接系统级动态库

在满足第三方库依赖方面，通常有两种途径：

  1. 通过 Zig 构建系统管理这些库（参见包管理器机制）。
  2. 直接使用宿主操作系统已经安装好的系统库文件。

对于上游开源项目的维护者而言，通过 Zig 构建系统获取并集成这些第三方库阻力最小，同时也把完整的构建配置权交还给了项目维护者。所有使用该方式编译的人都能获得完全一致且可复现的构建结果，它能在所有主流操作系统上无缝工作，并完美支持交叉编译。此外，这还允许项目极其精准地锁定整棵依赖树中所期望构建的绝对版本。在大多数情况下，这都是引入外部依赖库的推荐首选方案。

然而，对于将软件打包录入 Linux 发行版仓库（如 Debian、Arch 等）的维护者而言，他们更倾向于直接链接系统全局已经安装好的动态共享库。

zig build 的用户可以使用 --search-prefix 参数指定额外的目录，这些目录在查找静态库和动态库时会被视作“系统目录”。

就地生成与更新版本控制下的源码文件

在某些特殊场景下，项目可能会选择将自动生成的文件直接提交至版本控制系统（如 Git）。当这些生成文件极少变动，且更新它们需要安装繁重复杂的系统依赖（但仅在更新期间才需要这些依赖）时，这种做法会非常实用。UpdateSourceFiles 步骤正是用于实现这一需求。

请谨慎使用此功能；它不应该在常规构建流程中无条件触发，而应该显式绑定到一个独立的专用构建步骤上（例如 update-protocol）。

$ zig build update-protocol --summary all
Build Summary: 4/4 steps succeeded
update-protocol success
└─ WriteFile success
   └─ run proto_gen (protocol.zig) success 401us MaxRSS:1M
      └─ zig build-exe proto_gen Debug native success 1s MaxRSS:183M

运行该命令后，src/protocol.zig 文件便会被就地更新。
