有了 C++、D 和 Rust，为什么还需要 Zig？

没有隐式控制流

如果一段 Zig 代码看起来不像是跳转去调用某个函数，那它就确实没有调用。这意味着你可以确定，下面的代码只会先调用 foo()，再调用 bar()；即使不知道其中任何东西的类型，这一点也有保证：

var a = b + c.d;
foo();
bar();

隐式控制流的例子：

  • D 有 @property 函数。这类方法的调用写法看起来像访问字段，所以在上面的例子中，c.d 可能会调用函数。
  • C++、D 和 Rust 支持运算符重载，所以 + 运算符可能会调用函数。
  • C++、D 和 Go 有 throw/catch 异常（有时也叫 panic/recover），所以 foo() 可能抛出异常，导致 bar() 不被调用。（当然，即使在 Zig 中，foo() 也可能发生死锁，导致 bar() 不被调用，但这在任何图灵完备的语言中都可能发生。）

这一设计决策的目的是提高可读性。

没有隐式内存分配

在堆内存分配上，Zig 采取不插手的做法。Zig 没有 new 关键字，也没有任何会使用堆分配器的语言特性（例如字符串拼接运算符[1]）。堆这一整套概念由库和应用代码管理，而不是由语言管理。

隐式内存分配的例子：

  • Go 的 defer 会在函数局部的栈上分配内存。这种控制流的工作方式本身就不直观，而且如果在循环中使用 defer，还可能导致内存不足。
  • C++ 协程为了调用协程会分配堆内存。
  • 在 Go 中，函数调用可能导致堆分配，因为 goroutine 分配的栈很小，调用栈足够深时就需要调整栈的大小。
  • Rust 标准库的主要 API 在内存不足时会 panic，而接受分配器参数的替代 API 只是事后补上的（参见 rust-lang/rust#29802）。

几乎所有带垃圾回收的语言都到处散布着隐式内存分配，因为垃圾回收器在回收一侧掩盖了这些分配的痕迹。

隐式内存分配的主要问题在于，它妨碍了一段代码的可复用性，不必要地限制了这段代码可以部署的环境。简单来说，有些使用场景必须能够确信控制流和函数调用不会带来内存分配这一副作用，因此，只有真正能提供这种保证的编程语言，才能满足这些场景。

Zig 的标准库中有提供堆分配器、使用堆分配器的功能，但这些都是可选的标准库功能，并没有内置于语言本身。只要从不初始化堆分配器，就可以确信程序不会进行堆分配。

标准库中每个需要分配堆内存的功能，都通过接受一个 Allocator 参数来完成分配。这意味着 Zig 标准库支持独立环境（freestanding）目标。例如，std.ArrayList 和 std.AutoHashMap 可以用于裸机编程！

自定义分配器让手动内存管理变得轻松。Zig 有一个调试分配器，即使出现释放后使用和重复释放，也能保持内存安全。它会自动检测内存泄漏并打印对应的栈跟踪。arena 分配器可以把任意数量的分配合并为一个，一次性全部释放，而不必逐个管理每次分配。专用分配器则可以针对特定应用的需求，提升性能或改善内存使用。

[1]：实际上确实有字符串拼接运算符（更准确地说是数组拼接运算符），但它只在编译时起作用，所以仍然不会在运行时进行任何堆分配。

对不使用标准库的一等支持

正如上文所说，Zig 的标准库完全是可选的。每个标准库 API 只有在用到时才会编译进程序。无论链接 libc 还是不链接 libc，Zig 都同样支持。Zig 对裸机开发和高性能开发都很友好。

这样可以两全其美：例如在 Zig 中，WebAssembly 程序既能使用标准库的常规功能，生成的二进制文件又比其他支持编译为 WebAssembly 的编程语言更小。

适合编写库的可移植语言

代码复用是编程的终极理想之一。遗憾的是，实践中我们发现自己一次又一次地重新发明轮子。这往往也是有道理的。

  • 如果应用有实时性要求，那么任何使用垃圾回收或其他不确定性行为的库都不能作为依赖。
  • 如果一门语言让忽略错误变得太容易，就很难验证一个库是否正确处理并向上传递了错误。这时人们往往想抛开这个库，自己重新实现一遍，因为这样才能确定所有相关错误都得到了正确处理。Zig 的设计让程序员最省事的做法就是正确处理错误，因此可以有相当的把握认为，一个库会正确地向上传递错误。
  • 从现实情况看，C 目前确实是用途最广、可移植性最好的语言。任何不能与 C 代码交互的语言，都有被边缘化的风险。Zig 正尝试成为新的、适合编写库的可移植语言：一方面让外部函数遵循 C ABI 变得简单直接，另一方面引入安全机制和语言设计，防止实现中出现常见的 bug。

适用于现有项目的包管理器和构建系统

Zig 不仅是一门编程语言，还是一套工具链。它自带构建系统和包管理器，即使在传统的 C/C++ 项目中也很有用。

你不仅可以用 Zig 代码代替 C 或 C++ 代码，还可以用 Zig 替代 autotools、cmake、make、scons、ninja 等工具。在此之上，它还提供了针对原生依赖的包管理器。即使项目的全部代码都是 C 或 C++，这个构建系统也同样适用。例如，将 ffmpeg 移植到 zig 构建系统之后，只需下载 50 MiB 的 zig，就能在任何受支持的系统上为任何受支持的系统编译 ffmpeg。对开源项目来说，这种简化的从源码构建（甚至交叉编译）的能力，可能决定能否赢得宝贵的贡献者，还是失去他们。

apt-get、pacman、homebrew 等系统包管理器对终端用户的体验至关重要，但可能满足不了开发者的需求。一个语言专属的包管理器，可能决定项目是没有贡献者还是有很多贡献者。对开源项目来说，光是让项目成功构建就很困难，这对潜在贡献者是一道很大的门槛。对 C/C++ 项目来说，有依赖可能是致命的，在没有包管理器的 Windows 上尤其如此。即使只是构建 Zig 本身，大多数潜在贡献者也会被 LLVM 依赖难住。Zig 让项目可以直接依赖原生库，无需指望用户的系统包管理器提供正确的版本；而且无论使用什么系统、面向什么目标平台，几乎都能保证项目第一次就构建成功。

其他语言也有包管理器，但不能像 Zig 这样消除烦人的系统依赖。

Zig 可以用一门合理的语言取代项目的构建系统：它通过声明式 API 构建项目，同时提供包管理，从而让项目能够真正依赖其他 C 库。能够拥有依赖，就能构建更高层的抽象，可复用的高层代码也会因此大量涌现。

简单

C++、Rust 和 D 的特性太多，多到会让人无法专注于正在开发的应用本身的含义。你会发现自己在调试对编程语言的理解，而不是调试应用本身。

Zig 没有宏，但依然足够强大，能以清晰、不重复的方式表达复杂的程序。就连 Rust 的宏也有像 format! 这样的特殊情况，它是在编译器内部实现的。而在 Zig 中，等效的函数在标准库中实现，编译器里没有任何特殊处理的代码。

工具

Zig 可以从下载页面下载。Zig 提供 Linux、Windows 和 macOS 的二进制归档文件。下面列出其中一个归档文件包含的内容：

  • 下载并解压一个归档文件即可完成安装，无需任何系统配置
  • 静态编译，没有运行时依赖
  • 支持使用 LLVM 生成优化的发布构建，同时使用 Zig 自己的后端获得更快的编译速度
  • 另外还支持输出 C 代码的后端
  • 开箱即可交叉编译到大多数主流平台
  • 附带 libc 的源码，需要时会为任何受支持的平台动态编译
  • 包含支持并发和缓存的构建系统
  • 支持编译 C 和 C++ 代码，并提供 libc 支持
  • 通过 zig cc 直接替代 GCC/Clang，命令行兼容
  • Windows 资源编译器
